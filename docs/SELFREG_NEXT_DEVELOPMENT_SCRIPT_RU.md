# SelfReg AI: рабочий скрипт дальнейшей разработки

Дата фиксации: 2026-06-07.

Статус: локальная разработка продолжается. Коммит, push и redeploy не выполняются до отдельного решения.

## Исходная позиция

Проект уже ушел от свободного чат-бота к управляемому приложению:

- подросток проходит пять этапов саморегуляции;
- педагог видит историю ответов и событий;
- LLM используется для формулировки обратной связи внутри выбранного сценария;
- Supabase становится опорной базой истории;
- поддерживаются разные AI-провайдеры.

Ключевой принцип:

- психологическая модель живет в коде и данных;
- LLM отвечает за язык и вариативность фидбека;
- маршрут прохождения не должен зависеть от произвола модели;
- `clarify`, `back`, `retry`, `skip` являются нормальными событиями процесса.

## Что уже подтверждено проверками

- A/B-сценарии выбираются программным движком до вызова провайдера;
- B-сценарий реагирует на давление, жесткость, страх провала и импульсивность;
- `clarify` не должен перебивать явный B-сигнал;
- повтор после уточнения не замыкает подростка в бесконечный `clarify`;
- неучебный контекст допустим: спорт, творчество, общение, привычки;
- Supabase сохраняет русские строки без ломки кодировки;
- кнопка `Назад` сохраняет первую попытку и фиксирует отдельное событие возврата;
- локальный production build проходит.

## Порядок дальнейшей работы

### 1. Формализовать ядро модели

Цель: довести `lib/selfreg-flow-machine.ts` до полноценной машины переходов.

Нужно явно описать события:

- `ANSWER`
- `CLARIFY_REQUEST`
- `BACK`
- `RETRY`
- `SKIP`
- `COMPLETE`

Нужно зафиксировать правила:

- `ANSWER` и `SKIP` двигают этап вперед;
- `CLARIFY_REQUEST` оставляет на текущем этапе;
- `BACK` возвращает к предыдущему этапу без потери истории;
- `RETRY` фиксирует повторную попытку на том же этапе;
- завершение наступает только после корректного прохождения пяти этапов.

### 2. Расширить тестовую матрицу подростковых ответов

Нужно покрыть тестами:

- короткий, но содержательный ответ;
- пустой или слишком общий ответ;
- давление на себя;
- страх провала;
- беспомощность;
- импульсивный ответ;
- неучебную цель;
- непонимание вопроса;
- возврат назад;
- повтор после уточнения;
- сохранение правильного вопроса после возврата.

### 3. Усилить связку `ответ -> сценарий -> фидбек -> следующий вопрос`

Цель: убрать ощущение, что следующий вопрос живет отдельно от только что данного ответа.

Нужно:

- усиливать stage-specific правила в `scenario-engine`;
- учитывать историю ответа при выборе следующего вопроса;
- различать короткий осмысленный ответ и ответ, требующий уточнения;
- ослабить шаблонность локального fallback-фидбека.

### 4. Довести teacher dashboard

Dashboard должен явно показывать:

- первую попытку;
- уточнение вопроса;
- возврат назад;
- повторную попытку;
- пропуск;
- A/B только для содержательных ответов;
- источник фидбека: provider / normalized fallback / mock;
- краткую интерпретацию траектории без ярлыков.

### 5. Согласовать Supabase-схему с кодом

База должна штатно хранить:

- `provider`
- `model`
- `response_mode`
- `event_type`

После миграции нужно повторить:

- UTF-8 roundtrip;
- session flow test;
- проверку teacher dashboard на свежих данных.

### 6. Провести визуальный QA приложения и лендинга

Проверить:

- русскую и английскую версии;
- отсутствие наложений текста;
- корректность переключения языка;
- понятность подросткового сценария;
- читаемость dashboard;
- отсутствие технических формулировок в витринной части.

### 7. Подготовить selective staging

Только после локальной проверки:

- разделить изменения на логические группы;
- отдельно приложение, отдельно лендинг;
- исключить `.env.local`, временные логи и мусор;
- затем отдельно принять решение о commit/push/redeploy.

## Ближайший практический шаг

Следующий технически правильный шаг:

1. Добить явную матрицу `stage x event x next-state`.
2. Затем усилить `scenario-engine` по этапам 1..5.
3. После этого проверить цикл на живых сценариях A/B/clarify/back/retry.

И только потом переходить к следующему уровню polish.
